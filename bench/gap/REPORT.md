# Gap attribution against LLVM `-O2`

**Status: roadmap Goal 1, step 1 is done.** Every benchmark that takes more
than 0.1 ms has been measured and attributed: each extra executed instruction
belongs to exactly one cause bucket below (or to the explicitly described
`other` bucket), and the bucket deltas sum to the total instruction delta.
The numbers, per-block counts, per-function counts and category counts
underneath this report are reproducible with `bench/gap/run.sh` on the same
machine.

- machine: Apple M4 Pro, 14 cores, 48 GB, macOS arm64 (`darwin-arm64-local`)
- commit measured: `92f976a` (the suite history already in `bench/history/`)
- seeds: `0, 1, 42, 18446744073709551615`

## Method

### Modules

`bench/gap/build.py` uses the same source preparation, dependency resolution
and compile paths as `bench/run.py`; it only skips the timing/startup
machinery. It reuses `bench/work/` so the compiler sees the same absolute
paths, and every rebuilt module is byte-identical to the module the suite
measured at `92f976a` (checked by SHA-256 in `bench/gap/work/modules/`). The
LLVM reference is the same module built by the pinned nightly with
`-C opt-level=2`, both sides with `simd128` off.

### Dynamic instruction counting

`bench/gap/src/instrument.rs` re-encodes each function body unchanged and
inserts, before every basic-block entry,

```wat
global.get $__gap_bN
i64.const 1
i64.add
global.set $__gap_bN
```

Each `__gap_bN` is an exported mutable `i64` global. The sequence has no net
operand-stack effect, so block types, labels and branch depths are untouched;
the original instruction stream is encoded through `wasm-encoder`'s
`RoundtripReencoder`. The companion metadata records, per block, its static
instruction count, category counts, direct call targets, stack/heap load and
store counts, and whether a compare+branch sequence guards a panic path.
Dynamic instructions are therefore `sum(block executions × static instructions
in the block)`; there is no per-instruction counter and no perturbation of the
original opcodes.

`bench/gap/src/measure.rs` runs the instrumented module in Wasmtime, calls
`run(seed)`, reads the counters **before** calling `out_ptr()`/`out_len()` (so
those helpers are not counted), and checks the result and output bytes. Counts
are summed over the four suite seeds; per-seed counts are in
`results/counts/*.counts.json` (git-ignored but regenerated by the script).

Categories: local.get/set/tee; loads/stores split into shadow-stack and
non-stack by a flow-insensitive taint of the `__stack_pointer` global through
locals; direct/indirect calls (with targets; per-target direct counts are in
`analysis.json`, per-call-site targets and type indices in the per-seed meta);
branches; integer and float
arithmetic and comparisons; conversions; constants; globals; memory
size/grow/copy/fill; bounds-check-shaped compare+branch-to-panic; and `other`.
Structural markers (`block`/`loop`/`if`/`else`/`end`) are not counted as
executed instructions, on either side.

Indirect calls are counted by category but not resolved to a dynamic callee:
they are 11,328 in `b_alloc`, 3,929 in `sort`, 4,096 in `generated_stress`,
371 in `scene`, 39 in `collections` and a handful elsewhere. They are a small
fraction of every gap; the direct-call tables cover the hot targets.

The stack taint is an over-approximation: a local is "stack" if any assignment
to it can derive from `__stack_pointer`; this can only mislabel a heap access
as stack, not the reverse. The bounds-check detector recognises both
`i32.lt_u; br_if -> panic` and the more common `i32.lt_u; if ... else panic`
shape, resolving branch targets through the structured control stack.

### Attribution rules

Each instruction is assigned once, in this priority order:

1. **Software operations** — an instruction in a function identified as a
   software routine for an operation wasm can express directly
   (`compiler_builtins::mem::{memcpy,memset,memmove}`, `copy_forward`,
   `libm`/`sqrt`/`floor`/`ceil`/`trunc`/`nearest`/`widen_mul`/`__multi3`, ...),
   or a direct call to such a function. Sub-buckets are `soft_memory`,
   `soft_math`, `soft_other`, `soft_call`.
2. **Values in memory / register moves** — shadow-stack loads/stores and
   `local.get`/`local.set`/`local.tee`. This is the traffic SROA/mem2reg and
   inlining remove; wasm locals are not memory, but this bucket is the
   register-shuffling half of the same "value lives in a slot" problem. Its
   sub-buckets keep stack loads/stores separate from local moves.
3. **Bounds checks** — the compare and branch belonging to a guarded panic
   path.
4. **Too little inlining** — the call/return instructions themselves (a call
   to a software routine is counted under cause 1 instead). The memory traffic
   that inlining also removes is counted under cause 2, not twice here.
5. **Loop optimisation** — `br`, `br_if`, `br_table` (loop control/back-edges).
   Unrolling/strength reduction also affects the arithmetic in `other`; that
   is reported, not silently assigned here.
6. **Other** — everything left: constants, integer arithmetic not classified
   as address/local traffic, float arithmetic and comparisons, conversions,
   heap loads/stores, globals, select/drop, memory size/grow.

The table subtracts LLVM's count in the same bucket, so the per-cause deltas
sum to `ours - LLVM` exactly. A negative entry means LLVM executes *more* in
that bucket (for example LLVM keeps a `br_if` where our code has a `br`, or
LLVM's unrolled code has more constants). That is why some causes are slightly
negative; it is not lost accounting.

**Caveat on bulk memory.** LLVM's `memory.copy`/`memory.fill` count as one
wasm instruction while our `compiler_builtins` routines count one instruction
per byte-loop step. That exaggerates the instruction gap for the memory
routines, but the execution measurements agree with the direction and the
native `memory.copy` is genuinely much cheaper, so the ranking is unaffected.
The report calls this out wherever it matters.

## Per-program attribution

The cause columns are shares of the total extra executed instructions; the
all-program table with absolute numbers is in the appendix. The hot-function
tables and full WAT are under [`results/hot/`](results/hot/).

### nbody — 5.07×, 4.40G extra instructions

81% of the gap is `memory`: our code executes 3.32G local moves and 1.01G
shadow-stack loads/stores, and after subtracting LLVM's traffic the net extra is
3.55G. LLVM's whole program is inlined into `run` (1.80G instructions);
ours keeps one `nbody::body` (6.20G) with 2,649M `local.get` against LLVM's
553M, and 477M/536M stack loads/stores against LLVM's ~0. There are also 238M
bounds-check instructions (LLVM: 39M) and 538M of `other` (205M constants,
234M integer arithmetic, 79M integer compares). LLVM uses `local.tee` 197M
times where we use 59M: its values stay in locals across uses, ours are
re-materialised.

This is the clearest SROA/mem2reg case: the `[f64; 3]` bodies and the
per-step state live in stack slots, and every use reloads them. Removing the
targeted memory traffic alone estimates 5.07× → **2.17×** (upper bound);
subtracting bounds checks as well gives **~1.98×**.

### sha256 — 12.33×, 320.7M extra instructions

91% is one software routine: `compiler_builtins::mem::impls::copy_forward`
executes 287.1M instructions, 79% of the whole program. It is called 65,610
times per seed, 64 times per `compress` call, each time with the constant
length **256**. The WAT shows why:

```wat
;; ours: sha256::compress, once per round
local.get 1
local.get 8
i32.const 256
call $memcpy
```

`local.get 8` is the address of the static K table and `local.get 1` a stack
slot: every round copies the entire 256-byte constant table into the shadow
stack before indexing it. LLVM loads K directly:

```wat
;; LLVM -O2, inside run (compress is inlined)
local.get 4
i32.const 1049036
i32.add
i32.load
```

The rest is smaller: 18M memory (6%), 2.2M bounds, 9.3M other. Mapping the
memcpy to `memory.copy` would cut the instruction count but still copy 16 MB
per seed; the root fix is to address the static array directly instead of
materialising it. That single change targets **91% of the gap**; the
single-fix estimate is 12.33× → **2.47×**, and removing the remaining local
traffic takes it to **~1.78×**.

### sort — 12.22×, 1.11G extra instructions

84% is again software memory: 936M, of which 831M is `copy_forward`. The calls
are mostly **8-byte** swaps and partition moves:

```wat
;; ours: quicksort::partition_lomuto_branchless_cyclic
local.get 4
local.get 2
i32.const 8
call $memmove
...
local.get 2
local.get 4
i32.const 8
call $memcpy
```

LLVM emits two `i64.load`s and two `i64.store`s for the same swap. 5.3M calls
to `copy_forward` per four seeds execute 157 instructions each on average.
`sort::sift_down` is actually *smaller* in ours (76.4M vs 92.2M), so the sort
algorithm is not the problem; the memory intrinsics are. Memory adds 106.6M
(10%), inlining 10.5M, other 64.2M. Removing the small-copy overhead estimates
12.22× → **3.22×**; also removing the remaining local/stack traffic gives
**~2.19×**. The fix is to lower constant-size copies to load/stores (step 4) or
at minimum to `memory.copy` (step 2), not to tune the sort.

### math_e — 2.71×, 424.0M extra instructions

94% is software math: our `libm` code executes 711M instructions against LLVM's
239M. The hot functions are `HInt::widen_mul` (170.4M), `sqrt::goldschmidt`
(136.0M + 86.4M for the u64/u32 instantiations) and `sqrt::sqrt_round`
(120.3M); LLVM uses `__multi3` (72.0M), one `libm::sqrt::sqrt` (65.6M) and
`rem_pio2` (100.1M). LLVM does **not** emit `f64.sqrt` here either: the
benchmark calls `libm::sqrt`, so "map sqrt to the wasm instruction" as written
would not remove this gap. The win is inlining/optimising the libm software
implementation (step 5), and the upper bound is 2.71× → **1.06×** if our libm
code reached LLVM's instruction count.

### strings — 9.20×, 98.0M extra instructions

51% memory net (ours executes 47.6M local moves and 12.0M stack),
11% software memory (10.3M `copy_forward`), 35% other (12.5M constants, 12.2M integer arithmetic, 4.1M
globals, 4.1M heap). The hot functions are iterator/pattern machinery
(`CharIndices::next` 16.8M, `MultiCharEqSearcher` 16.4M,
`next_code_point` 8.5M, `Iter<u8>::next` 7.7M), i.e. small functions that LLVM
inlines into `run` and we call. Removing the memory traffic alone estimates
9.20× → **5.40×**; the address/constant residual adds another ~26%. This is a
step-5 inliner/SROA case, not a string-algorithm case.

### miniz_driver — 2.91×, 125.9M extra instructions

57% memory net (ours executes 95.4M local moves and 16.1M stack),
15% software memory (18.4M `copy_forward`/`memmove`), 4% bounds, 25% other (14.0M constants, 11.8M integer
arithmetic). LLVM fuses most of deflate into `compress_inner` (58.4M) and
`flush_block` (12.2M); ours keeps `compress_normal` (74.5M), `find_match`
(32.6M), `record_literal` (14.5M), `compress_lz_codes` (12.5M) and many
generic instantiations. Removing memory traffic estimates 2.91× → **1.96×**
and removing the small-copy routines **→ 2.67×**; together with bounds,
**~1.65×**. The module is also 5.03× larger, with 47.3KB of never-executed
functions (dead `compress_fast`, unused generic instantiations).

### matmul — 1.56×, 33.4M extra instructions

The instruction ratio is only 1.10× but execution is 1.56×. 94% of the extra is
memory net (31.3M, essentially all local moves: 187.7M ours against LLVM's
~156.4M) and 50% is bounds checks (16.8M); the `other` bucket is
negative because LLVM has 10.6M more constants than we do, and the float
arithmetic is identical (17.2M both). This is a pure "values in locals plus
checks" gap; SROA + bounds elimination estimates **1.37×**. It is a good
first target because the absolute instruction count is small and the fix is
well understood.

### mandelbrot — 1.06×, 186.6M extra instructions

Already at parity: the extra 44% instruction count does not translate into
execution time because the extra work is cheap integer/constant work around
the same floating-point loop. 43% memory (80.3M) and 60% other (54.7M
constants, 42.9M integer arithmetic, 7.4M integer compares, 6.9M conversions);
float arithmetic is identical (115.85M vs 114.94M). SROA/address folding
estimates **0.92×**, i.e. no urgency. This is a useful counter-example: a
large instruction-count gap is not automatically a large time gap.

### libm_driver — 3.25×, 179.7M extra instructions

95% software math. The libm-code share is 295.1M instructions against LLVM's
85.5M (whole program 302.7M vs 123.0M); LLVM has `__multi3` 28.8M,
`libm::sqrt::sqrt` 26.2M, `log1p` 12.3M, `atan` 10.0M and `pow` 9.3M. Same
root cause as `math_e`: inlining/optimising the libm implementation, not a
missing wasm instruction. Estimate 3.25× → **1.11×** if our libm code matched
LLVM's instruction count.

### hostcall_f — 1.00×, 3.8M extra instructions

At parity: 200k host calls dominate native time, so a 1.55× instruction ratio
does not matter. No fix is needed; it is the control case showing that the
method attributes instructions, not native host time.

### Finding 1: a constant 16,388-byte zero data segment (not compiler DCE)

Every module contains a 16,388-byte all-zero active data segment. It is the
benchmark prelude's `OUT` buffer (`[u8; 16_384]` plus its length), which is
zero-initialised. Wild materialises it as an explicit data segment; LLVM's
wasm-ld relies on linear memory being zero by default and emits only 478 B of
data for `a_add`. This is a fixed **16.4 KB** on every module:

- `a_add`: 34,622 B total; 18,417 B data, of which 16,388 B is this segment.
  Without it the module is 18,234 B (4.4× LLVM instead of 8.3×).
- `miniz_driver`: 253,510 B, 47,871 B data, 16,388 B zero; removing it saves
  6.5% of the module.
- Over all 21 programs it is 344,148 B of the 1.73 MB total.

This is a **Wild linker** issue, not one of the five compiler causes: omit
all-zero data segments and grow initial memory instead. It is the single
largest size win for small programs and costs nothing at run time. It is out of
scope for this analysis, but it should be filed with the linker work.

### Finding 2: dead panic/fmt/generic functions (38.5% of extra function bytes)

Comparing function bodies by name, 590,014 B of our code exists in functions
LLVM does not have; 227,255 B of that (38.5%) executes **zero** instructions on
any seed. The categories:

| category | functions | bytes | dead bytes |
| --- | ---: | ---: | ---: |
| allocator | 683 | 174,796 | 29,914 |
| generic instantiation | 830 | 166,052 | 62,533 |
| other core/compiler_builtins | 196 | 115,722 | 19,259 |
| panic/fmt machinery | 411 | 100,404 | 99,220 |
| software mem | 198 | 24,434 | 13,637 |
| libm software math | 55 | 8,606 | 2,692 |

Almost all panic/fmt bytes are dead (`core::fmt::Formatter::padding`,
`<usize>::_fmt_inner`, `panic_bounds_check`, `copy_from_slice` error paths),
but they remain reachable from the panic path and from bounds checks that the
compiler cannot prove away. `a_add` keeps 6,564 B of never-executed functions
and 1.5 KB of source-file-path strings; `miniz_driver` keeps 47,262 B of dead
functions (18% of its 253 KB), including `compress_fast` and unused generic
instantiations. LLVM removes them by inlining and dead-code elimination at
codegen time. This is a compiler-side size fix (emit only reachable
monomorphisations / strip panic formatting when `panic=abort`), not a linker
flag.

### Finding 3: Wild does run garbage collection

The linker is **not** the dead-code culprit. Compiling `a_add` through the
product pipeline three ways (`bench/gap/gc_test.sh`):

| variant | `a_add` bytes | `sha256` bytes |
| --- | ---: | ---: |
| default (Wild wasm GC on) | 34,630 | 50,079 |
| `-Clink-arg=--gc-sections` | 34,625 | 50,064 |
| `-Clink-arg=--no-gc-sections` | **1,347,548** | **1,356,409** |

Wild's wasm target enables `--gc-sections` by default (its own help says so)
and removes ~97.4% of the unreachable input. The remaining functions are
reachable from retained roots (panic paths, exported ABI, allocator); the fix
has to be on the compiler side. The small difference between default and
explicit `--gc-sections` is link-argument metadata, not GC behaviour.

## MIR optimisation experiment

`bench/gap/mir.py` rebuilds every program in our pipeline with extra
`-Z` flags passed to the compiler inside `rustc.wasm`; the product default is
unchanged. Variants: `mir3` = `-Zmir-opt-level=3`; `inline` = `mir3` plus
`-Zinline-mir=yes -Zinline-mir-threshold=100`. Compile/execution are medians of
3/5 runs over the same four seeds; every variant returned the same outputs as
LLVM `-O2` (difftest green).

| variant | exec geomean vs baseline | compile median | size median |
| --- | ---: | ---: | ---: |
| `mir3` | 0.997× | 1.007× | 1.000× |
| `inline` | 1.012× | 1.013× | 0.996× |

Per-program results, including `nbody`, `sha256`, `sort`, `math_e` and
`libm_driver`, are in [`results/MIR.md`](results/MIR.md) and
[`results/mir.json`](results/mir.json). There is **no execution win** anywhere
outside run-to-run noise; `inline` saves 0.4% of size on median (a few hundred
bytes per module) and `mir3` saves essentially nothing, while both add about
1% compile time. `sha256` and `sort` move by <2% despite the large MIR-visible
call graph: MIR inlining does not remove the shadow-stack copies because the
backend still materialises the values. This is an important negative result
for roadmap step 3: turning up pure-Rust MIR optimisation alone does not close
the gap; it must be paired with the backend SROA/inliner (step 5), or
deprioritised.

## Ranked fixes

Ranked by expected share of the measured gap across the suite. The per-program
estimates are **upper bounds from instruction counts** (remove the target
instructions and scale execution by the instruction ratio); they are useful for
ordering, not as promises. Confidence is about the instruction reduction and
the direction of the speed win.

### 1. Lower constant/small `memcpy`/`memmove`/`memset` (roadmap steps 2 and 4) — high confidence

The single biggest win. Two sub-cases:

- **8-byte/constant-size copies** (sort, collections, strings, smoke): emit
  `i64.load`/`i64.store` or `memory.copy` instead of a call to
  `compiler_builtins::mem::memcpy`. Sort alone: 936M extra instructions, 84% of
  its gap, from 5.3M calls averaging 157 instructions per 8-byte copy.
- **Constant-array materialisation** (sha256): do not copy the 256-byte K
  table into the stack per round; address the static array directly
  (`i32.const K; i32.add; i32.load`). SHA-256 alone: 91% of its gap.

Expected: `sha256` 12.33× → **~2.5×**, `sort` 12.22× → **~3.2×**,
`collections` 9.16× → ~5×, `strings` 9.20× → ~8.4×, `smoke` 3.82× → ~2×,
`miniz_driver` 2.91× → ~2.7×; suite geomean 3.53× → **~2.58×**. Confidence
high on instruction reduction; the native win is at least as large because
Wasmtime lowers `memory.copy` to native `memcpy` and inline load/store to one
move.

### 2. SROA/mem2reg plus a cost-model inliner (roadmap step 5) — high confidence

Removes the 3.55G of stack/local traffic in `nbody` (81% of its gap), 72M in
`miniz_driver` (57%), 50M in `strings` (51%), 31M in `matmul` (94%), and the
smaller local-move gaps elsewhere. Expected: `nbody` 5.07× → **~2.2×**,
`miniz_driver` → **~2.0×**, `strings` → **~5.4×**, `matmul` → **~1.4×**,
`mandelbrot` → ~0.9–1.1× (already parity). Confidence high that the traffic
disappears; the exact speed win depends on how much Wasmtime already coalesces,
which is why `nbody`'s 3.45× instruction ratio only produces 5.07× time.

### 3. Bounds-check elimination from range facts (roadmap step 6) — medium confidence

238M instructions in `nbody` (5% of gap), 16.8M in `matmul` (50% of its gap),
4.5M in `miniz_driver`, 2.2M in `sha256`. Expected: `matmul` 1.56× →
**~1.4–1.5×**, `nbody` 5.07× → ~4.9×, `miniz_driver` → ~2.85×. Confidence
medium: some checks are genuinely needed; the win comes from proving loop
indices against slice lengths, which step 6 explicitly targets.

### 4. Software maths: inline/optimise libm, do not expect a wasm instruction (roadmap step 5, not step 2 as written) — medium confidence

`math_e` and `libm_driver` are 94–95% software-math instructions, but LLVM also
calls `libm::math::sqrt::sqrt` (65.6M) and `__multi3` (72M); it does not emit
`f64.sqrt`. Mapping `sqrt` to the wasm instruction would not remove this gap
unless the benchmark or libm calls the intrinsic. The measured win is from
inlining/optimising the libm implementation (our `goldschmidt`/`sqrt_round`
split, `widen_mul` vs `__multi3`). Expected: `math_e` 2.71× → **~1.1–1.5×**,
`libm_driver` 3.25× → **~1.1–1.6×**. Confidence medium; this is a large
specialised inlining job, and the upper bound assumes matching LLVM's libm
instruction count.

### 5. Address/constant folding in loops (roadmap step 4) — medium confidence

The residual `other` bucket is mostly constants and integer address arithmetic:
`mandelbrot` 112.7M (60% of its gap), `nbody` 537.7M (12%), `sort` 64.2M (6%),
`miniz_driver` 31.2M (25%), `strings` 34.1M (35%). Folding constant offsets
into load/store offsets and dropping redundant extends targets part of this.
Expected: `mandelbrot` stays at parity (0.9–1.1×), `nbody` ~4.6×,
`miniz_driver` ~2.55×, `strings` ~7.2×; suite-level a few percent. Confidence
medium; the category mixes real arithmetic with address arithmetic, so the
upper bound is optimistic.

### 6. Size: omit zero data in Wild; emit only reachable code in the compiler (outside the five causes) — high confidence for the linker part

- Wild zero-data omission: −16,388 B on every module. `a_add` 34.6 KB → 18.2 KB,
  `miniz_driver` 253.5 KB → 237.1 KB; no speed effect. High confidence, but a
  linker change.
- Compiler DCE / panic-format stripping: 227 KB of never-executed functions
  over 21 programs, 47 KB in `miniz_driver`, 6.6 KB in `a_add`; plus 1.5–4 KB
  of file-path strings per module. Medium confidence; needs care not to remove
  paths that can actually panic. Together with the zero segment this is the
  bulk of the 3.9× size ratio.

### 7. MIR optimisations at the rustc level (roadmap step 3) — measured, no speed win; deprioritise

`-Zmir-opt-level=3` and `-Zinline-mir` gave 0.997×/1.012× execution geomean,
+1% compile, −0.4% size, outputs green. Do not make this the next fix; it is
necessary later but not sufficient without backend SROA (step 5).

### 8. Loop unrolling/vectorisation (roadmap step 7) — low priority until 1–4 land

The loop-control bucket is small (78M in `nbody`, negative elsewhere because
LLVM's `br_if` shape differs). LLVM's SHA-256 advantage includes full unrolling
and constant folding of the 64 rounds, but that sits behind the K-table copy;
`mandelbrot` is already at parity. Revisit after the memory/SROA work.
