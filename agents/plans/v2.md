# CogWasm V2: a function-granular, always-optimising Rust compiler

Draft, 2026-11-23. A plan for the next generation of CogWasm, written after
V1 reached a resident, incremental, hot-swapping edit loop (25 ms small edit,
103-157 ms plugin-sized on CI), a live in-browser REPL, and the first MIR
optimisation passes (step 5b). Nothing here is built yet unless it says so.
Goal numbers refer to [`ROADMAP.md`](../ROADMAP.md); the near-term queue is
[`next-steps.md`](next-steps.md).

## Targets

| axis | CogWasm V1 today | V2 target |
| --- | --- | --- |
| Edit -> result, one function changed, large program (100k lines) | 2,191 ms p50, 2,224 ms p90 (98k-line generated program, local macOS, 5 edits; 1.99 s build + 0.19 s swap) | **<= 20 ms p50, <= 50 ms p99**, optimised code |
| Edit -> result, small program | 25 ms (CI) | **<= 5 ms** |
| Clean checkout -> running, large program | 18.7 s cold program build with the toolchain prebuilt (local macOS) | **<= 1 s** with a warm shared store, <= 20 s cold |
| Steady-state speed of the output | about 2.8x of LLVM `-O2` (executed wasm instructions) | **<= 1.0x** of LLVM `-O2` on the suite; ahead of it where vectorisation or PGO applies |
| Language fidelity | real rustc; difftest against LLVM on every push | real rustc; **zero known wrong-result bugs**; rustc run-pass pass rate published |
| Same compiler for release | yes | yes, deterministic and reproducible |
| Where it runs | anywhere wasm runs, including the browser | same, plus native via Wasmtime AOT |
| Binary size | median 46 KB on the suite | **<= LLVM `-Oz`** after the size tier |

The latency targets rest on one rule: no function is optimised twice,
anywhere, for anyone. Output speed is capped by what LLVM achieves on scalar
code, so the target there is parity, and beating it only where vectorisation
or profile-guided decisions honestly can. Fidelity is not a number, but it
comes first: a faster compiler that is sometimes wrong is not an improvement.

## Principles

1. **Real rustc semantics, always.** We mutate rustc's middle and back end as
   much as we like, but the front end stays rustc's: parsing, macros, name
   resolution, type checking, trait solving, borrow checking and diagnostics.
   No reimplementation of the language.
2. **Every build is optimised.** No adaptive JIT and no fast-then-slow tiers:
   performance must be predictable from the first build. Tier 2 exists only
   to make the binary smaller, never faster or slower.
3. **The function is the unit of everything:** change detection, optimisation,
   caching, linking, hot patching and lazy loading.
4. **Never do the same work twice.** Optimised function bodies are stored by
   content hash and shared across edits, projects, machines and users. A
   function is optimised once in the world.
5. **Faster must never mean wrong.** Every new pass is gated by difftest,
   adversarial programs, a sysroot built with the pass on, and the rustc
   run-pass suite, before it is on by default.
6. **Pure Rust, no LLVM**, wasm everywhere, deterministic output.

## Architecture

```text
             edit
              |
  [1] resident rustc (serving guest, in-memory incremental, parallel front end)
              |  per-function MIR + stable identity + content hash
  [2] function graph  --hash hit-->  [5] global optimised-function store
              |  miss                          ^
  [3] optimiser: summaries, inliner, SROA/mem2reg, loop opts, vectoriser, PGO
              |
  [4] Cranelift back end -> one relocatable wasm body per function ---'
              |
  [6] stitcher: copy-and-patch module assembly (no linker in the edit loop)
              |
  [7] runtime: table-slot hot patching, lazy stubs, state kept
              |
  [8] tier 2 in the background: size-only rebuild, swapped in when ready
```

### [1] Resident front end

Built on V1's serving guest (patch 0007) and in-memory metadata cache.

- Keep rustc's incremental dependency graph and query results **in memory**
  across edits instead of serialising and re-reading them (10-30 ms per edit
  today). Mutation: an in-memory backend for `rustc_incremental`'s save/load.
- **Parallel front end:** turn on rustc's parallel front end in the guest with
  host-provided threads (Wasmtime shared memory; Web Workers in the browser).
- **Macro expansion cache:** reuse expansions of unchanged items across edits
  (about 19 ms of every compile today).
- Proc macros compiled to wasm and run in a host-provided instance (G3.1), so
  the front end covers derive-heavy crates.

### [2] The function graph and identity

- Mutation in `rustc_monomorphize`: in the edit loop, **one function per
  codegen unit** (today an edit rebuilds the CGU holding a whole module's
  functions, about 30% of `strings`).
- Each monomorphised function gets a stable identity and a **content hash**:
  its optimised-MIR fingerprint, the hashes of the types and layouts it uses,
  and the hashes of every callee it imported for inlining (ThinLTO-style
  import lists). Equal hash means equal output, which is what makes the
  store, deduplication and correctness checks possible.
- Shared generics: instances of `core`/`alloc`/`std` generics (`Vec<u32>`,
  iterator chains over slices) resolve to the store first.

### [3] The optimiser (MIR, where rustc's type and alias facts live)

Starts from step 5b's passes (the loop-aware inliner, patch 0006; the capture
analysis and sound loop-field hoist, patch 0008).

- **Summary-based cross-function optimisation:** per-function summaries
  (capture, purity, cost, read/write sets) drive inlining and promotion, so a
  changed callee invalidates only the functions that imported it.
- **SROA with drop expansion** and partial aggregate splitting, so `Vec` and
  `String` locals split into fields; **stack-to-locals promotion** of
  everything that does not escape (the bulk of the 2.8x gap is linear-memory
  traffic).
- **Loop optimisation:** invariant code motion, bounds-check elimination from
  range facts, unrolling.
- **Auto-vectorisation to `simd128`:** straight-line and loop vectorisation of
  slices and arrays, after explicit SIMD works end to end.
- **Offline profile-guided optimisation:** the instrumented counters already in
  `bench/gap` record hot blocks; profiles are stored per function hash and
  used by later builds. Not adaptive at run time.
- Because each function is optimised once in the world, the optimiser can
  spend far more per function than a JIT can: fuller equality saturation on
  hot functions, and superoptimisation of the hottest loops, cached.

### [4] Cranelift mutations

- Emit **one relocatable wasm function body per function**, with relocation
  records for function indices, globals and data addresses: the "stencil"
  the stitcher patches.
- Wasm-specific code generation: allocate wasm locals as registers (fewer
  locals, fewer `local.get`/`local.set`), fold constants into memory offsets
  (started in V1), and select `simd128` instructions for vectorised MIR.
- Extend the ægraph mid-end rules for the patterns our MIR produces, and give
  hot functions a larger rewrite budget.

### [5] The global optimised-function store

- Content-addressed: hash -> optimised wasm body, its relocations, its
  summary, its profile. Local first, then a shared remote store (an HTTP
  cache any team, CI runner or browser can read).
- **Pre-filled** with the monomorphised `core` and `alloc` instances common
  programs use, built by CogWasm itself, so a new project mostly hits.
- Signed and verified by hash; the hash covers the compiler's own identity,
  so a compiler change can never return a stale body.

### [6] The stitcher

- Assembles the output module from stored bodies by **copy-and-patch**:
  lay out the functions, patch relocations, emit the tables and data. No
  general linker in the edit loop. Wild stays for release links and anything
  the stitcher does not handle.
- Deduplicates identical functions for free (equal hashes).
- Output is deterministic: the same inputs give the same bytes.

### [7] Runtime: hot patching and lazy loading

- Every call goes through a wasm table slot. A changed function is a **table
  patch** into the running instance, not a module swap; state, stack and
  memory stay. Layout or ABI changes fall back to V1's whole-module swap with
  state hand-over.
- **Lazy stubs** for large programs: functions not yet needed start as stubs
  that fetch or compile their body on first call, so start-up is proportional
  to what runs, not to program size.
- Wasmtime's per-function compile cache (V1) and the browser's own caching
  keep the native compile per changed function small.

### [8] Tier 2: size only

- In the background, after a build: whole-module size passes (dead-code and
  dead-data removal, identical-function folding, a size-tuned inlining policy,
  learned as MLGO does, wasm-level shrinking), then swapped in.
- Never changes speed in either direction; checked by the same counters.

### GPU (research track)

Compiling Rust does not map onto GPUs. The programs we compile can: offload
data-parallel loops (marked or detected) to WebGPU/wgpu compute shaders,
first for `nbody`/`matmul`-style kernels, with a CPU fallback and the same
difftest-style checking.

## What we change in rustc and Cranelift

| component | change |
| --- | --- |
| `rustc_incremental` | in-memory save/load for the resident compiler |
| `rustc_interface` / driver | serving loop (done, 0007), parallel front end in the guest |
| `rustc_expand` | expansion cache for unchanged items |
| `rustc_monomorphize` | one function per CGU in the edit loop; store lookup for shared generics |
| `rustc_middle` / query system | stable function identities and content hashes; summaries |
| `rustc_mir_transform` | inliner (0006), capture analysis and hoist (0008), SROA with drop expansion, stack-to-locals, loop opts, vectoriser, PGO consumer |
| `rustc_codegen_cranelift` | per-function relocatable output, store integration |
| Cranelift / clif-to-wasm | wasm local allocation, `simd128` selection, ægraph rules, relocation stencils |
| Wild | stays for release links; the stitcher replaces it in the edit loop |
| Wasmtime host / browser runtime | table-slot hot patching, lazy stubs, store client |

All of it stays a reviewed patch series in `compiler/patches/`, rebased with
each pinned nightly; the cost of carrying it is a stated risk below.

## Phases

Each phase ends with numbers in CI, and nothing is on by default until its
correctness gate passes. The `cogwasm-bench` tool in
[`crates/cogwasm-bench`](../../crates/cogwasm-bench) reports the build-speed,
edit-loop, execution, instruction-count and size measurements these numbers
come from; see [`bench/README.md`](../../bench/README.md#rust-benchmark-tool-cogwasm-bench).

| phase | delivers | done when |
| --- | --- | --- |
| **0. Measure** | how much of an edit's rebuilt code is unchanged functions; a 100k-line benchmark program; edit-loop numbers at that size | the cacheable share and the large-program baseline are published |
| **1. Function granularity** | one function per CGU, stable hashes, local store, stitcher, table-slot hot patching | single-function edit <= 50 ms p50 on the large program, byte-identical to a full build |
| **2. Resident front end** | in-memory incremental, macro cache, parallel front end | small edit <= 5 ms, single-function edit on the large program <= 20 ms p50 |
| **3. Optimiser to parity** | step 5b finished (SROA with drop expansion, stack-to-locals), loop opts, summaries on by default | suite <= 1.2x then <= 1.0x LLVM `-O2`; difftest, adversarial set and passes-on sysroot green |
| **4. Vectorise and profile** | explicit `simd128` end to end, auto-vectorisation, offline PGO | beats LLVM `-O2` (scalar) on the vectorisable benchmarks |
| **5. Size tier** | tier-2 size passes, learned inlining policy | <= LLVM `-Oz` size with unchanged speed |
| **6. Shared store and scale** | remote store, pre-filled `core`/`alloc`, lazy stubs | clean checkout -> running a large program <= 1 s with a warm store |
| **7. Ecosystem** | proc macros, `std` for WASI, a resolver (Goal 3) | `serde`-derive and multi-crate crates.io programs build |
| **8. GPU research** | data-parallel offload for marked kernels | measured win with identical results |

Phases 1-2 and 3-4 can run in parallel: they touch different code (front end,
store and runtime versus MIR passes and Cranelift).

## Correctness, always on

- Difftest against LLVM on every push, with and without every pass (V1).
- The adversarial corpus for every pass that relies on alias or capture facts
  (started with 0008's seven programs).
- `core`/`alloc` compiled with every pass on, then difftest against that
  sysroot (caught a real miscompile in 0008's first version).
- rustc's run-pass tests through the pipeline, pass rate published (open
  roadmap item).
- Store integrity: a sample of store hits recompiled cold and compared
  byte for byte in CI.
- Fuzzing with rotating seeds (Q2).

## Risks and honest limits

- **Carrying deep rustc patches.** Every nightly bump means rebasing them.
  Mitigation: keep each mutation small and behind its own flag until proven,
  and upstream-shaped where possible.
- **Content-addressing Rust is hard.** Generics, traits, macros and
  incremental query identities make "same hash, same output" subtle; a wrong
  key is a stale-code bug. Mitigation: hash conservatively and audit hits
  (above).
- **First compiles still cost.** A function nobody has compiled before pays
  for full optimisation once; the targets assume a store warm for
  dependencies, which phase 6 provides.
- **Precedent says this is hard to finish.** Rust's own "relink, don't
  rebuild" goal was not completed, and Zig's in-place patching is still
  experimental. Phase 0 measures the payoff before phase 1 commits to it.
- **Speed parity is not guaranteed.** The 2.8x -> 1.0x gap needs SROA, alias
  and vectorisation work that LLVM spent years on; phase 3's acceptance is a
  number, and the plan says so if it is missed.
